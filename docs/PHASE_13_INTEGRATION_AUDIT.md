# Phase 13 — Cross-module integration audit

**Status:** In progress; local SQLite-backed integration evidence is available, but Phase 13 is not complete.  
**Branch:** `arena/e6c9b4f7-crownd-2-0`  
**Scope:** Repair integration behavior in the existing CROWND product. No UI redesign, real payment gateway, or real payout transfer.

## Audit approach and evidence boundary

Reviewed the commerce, attribution, conversion, reward/ledger, analytics, campaign/application, admin/dispute, notification and migration paths, their SQLAlchemy models, and existing backend tests. Tests use disposable in-memory or temporary SQLite databases. No connected Supabase database or production data was accessed. SQLite tests do not prove PostgreSQL row-lock behavior or concurrent transaction correctness.

## Journey findings and disposition

| Journey / risk | Finding | Change or evidence | Remaining verification |
|---|---|---|---|
| Customer → referral → mixed cart → conversion → reward/ledger → creator analytics | A conversion is order-scoped while attribution is line-scoped. Creator conversion views that trusted only the conversion's primary creator/referral could omit other creators in a mixed cart or expose the full-order amount as that creator's attributed amount. | Creator views now include orders with that creator's attributed line items and return creator-scoped attribution lines/amounts. Legacy conversion payloads without item-level attribution retain their stored values. Mixed-cart test now asserts one creator-scoped line and amount for each creator; existing tests assert persisted conversion/reward/ledger state and role-scoped analytics. | No PostgreSQL query-plan/performance validation. Analytics semantics for mixed orders should receive product-owner confirmation before changing any external reporting contract.
| Checkout → COD collection → reward calculation | COD rewards are created on collection, so changing campaign/rule terms between checkout and collection could otherwise alter the commission. | New nullable `OrderItem.reward_snapshot` freezes checkout attribution and reward terms; reward creation validates the snapshot and calculates COD rewards from it. Test changes the campaign rate after checkout and verifies the persisted reward uses the original rate. | Legacy rows without snapshots intentionally retain the compatibility calculation path; no production-data backfill was run.
| Dispute → reward hold → resolution | Disputes were not consistently associated with reward review state; release queries could read the old dispute status when session autoflush was disabled. | Linked rewards are held without changing ledger entries; resolving one case restores status only when no other linked case remains. The status transition is explicitly flushed before release checks. Persisted-state COD/reward test asserts hold, release, unchanged ledger IDs/amounts/directions. | An opt-in PostgreSQL overlapping-dispute test is present but skipped; race behavior remains unverified.
| Order cancellation/restock/reward invalidation | Existing cancellation uses a conditional order-state update, restores reserved stock and cancels conversion/reward state before collection; repeat/late cancellation is rejected. | Existing commerce regression verifies inventory restoration and cancellation state. Order-item history is now append-only at ORM and migration DB trigger layers so historical item evidence is not rewritten. | SQLite suite only; no PostgreSQL checkout-vs-cancel contention test. Paid orders still require a separate refund workflow and are not cancellable here.
| Inventory / cart / checkout concurrency | Checkout locks the per-customer cart and cart items/products, with deterministic product-ID ordering and conditional stock decrement. Cart mutation routes were not consistently using the same cart-first locking order; repeated checkout could check idempotency before waiting on the cart lock. | Cart edits/deletes/clear now lock the cart before its items; checkout rechecks the idempotency key after obtaining the cart lock; first-cart creation uses a savepoint to recover the unique-user race. Existing tests cover stock bounds, cancellation restock, idempotent replay and sold-out handling. | These locking and concurrency properties require PostgreSQL multi-connection tests; not established by SQLite.
| Brand/creator suspension → commerce/campaign actions | Suspension hides seller content and revokes sessions; suspended creators could otherwise be accepted into campaigns or have rewards approved/simulated for payout. | Acceptance checks active brand/campaign/creator; campaign publication validates brand and explicitly selected products; reward approval/payout simulation rejects inactive creators. Existing lifecycle tests assert purchase denial and persisted inventory/order state. | No high-contention test of suspension racing acceptance, checkout, or payout simulation. Existing rewards remain historical; no records are deleted.
| Campaign lifecycle → eligible products | Campaign product configuration/publication can race with product activation or campaign state changes. | Campaign status/configuration and selected product updates now take row locks; publishing verifies explicitly selected products remain active and owned by the brand. | PostgreSQL deadlock/race tests remain outstanding; generic campaigns without explicit products retain prior behavior.
| Admin moderation and transitions | Existing moderation, application and order/dispute workflows use server-side ownership/role checks and audited transitions; concurrent invariants need database row locks. | Campaign/application and dispute reward rows are locked where state is coordinated. User lifecycle notifications use a deterministic event key based on the persisted admin audit event, preventing a time-derived/random key from defeating retries. Tests cover authorization, transition validation, audit persistence and session revocation. | No independent penetration test, concurrent PostgreSQL admin cohort test, or exhaustive endpoint fuzzing.
| Notification event propagation | Notification service already enforces recipient scope, category preferences, deterministic event keys, and encrypted outbox records. New order, collection, cancellation, campaign application and dispute events now notify relevant participants. | Notification tests cover idempotency/preferences/outbox behavior; commerce/admin tests exercise recipient-visible events and persisted business state. | No live SMTP acceptance or multi-worker PostgreSQL race test; email delivery is not claimed.
| Role-based analytics consistency | Mixed-cart revenue must be attributed from order items without double-counting or leaking customer data. | Creator and brand analytics use line-level attribution; creator conversion payloads now report the creator's own lines. Existing analytics tests cover order-item revenue splitting, ownership, private-field exclusion and filters. | No independent reconciliation against production analytics or external financial reporting.

## Financial and historical-data safeguards

- Ledger entries, reward events, and order-item snapshots reject ORM update/delete. Migration `0010_integration_snapshots` adds SQLite/PostgreSQL triggers for order-item immutability.
- Dispute holds alter reward review state only; they do not edit or delete ledger rows. Financial corrections continue to use append-only reversals.
- Checkout reward terms are added as nullable snapshot data; existing order/reward history is retained. No database was used for data backfill.
- Demo rewards remain non-payable simulations. COD rewards are generated only after administrator-recorded collection. CROWND records do not initiate a money transfer.
